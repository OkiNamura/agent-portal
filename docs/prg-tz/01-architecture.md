# 01. Архитектура

## 1. Два процесса, а не один

Игра делится на фазу сборки и фазу игры. Граница между ними — замороженная библия кампании.

```
ФАЗА A. Сборка (один раз, до первого хода)

  теги тона ──► генератор ТОНА  ──► tone.md  ┐
  описание мира ─► генератор МИРА ─► world.md ├─► библия кампании (после старта не меняется)
  форма героя ──► heroBlock()    ──► hero.md  ┘
  core.md (одно на все игры) ─────────────────┘

ФАЗА B. Игровой цикл (каждый ход)

  ввод игрока
      │
      ▼
  buildContext()            статика → закрытые арки → история → конспект прошлого → состояние → ход
      │
      ▼
  ведущий (gm)              проза; при структурном выводе — проза + дельта
      │
      ▼
  parseDelta() / reply.delta
      │
      ▼
  applyDelta()              детерминированная валидация и применение
      │
      ▼
  critique()                дешёвые правила, без модели
      │
      ▼
  лог (player + gm) → снимок хода → запись кампании на диск
      │
      ├─► state-агент (параллельно)   добирает изменения из прозы
      └─► summarizer (параллельно)    обновляет скользящий конспект
      │
      ▼
  ответ клиенту: проза, изменения, состояние, карты, расход
```

Асинхронно от хода: иллюстрация сцены по кнопке. Она не блокирует ход и не влияет на состояние,
кроме записи URL в `illustrations` или в карточку.

## 3. Поток одного хода по шагам

Нумерация — реальный порядок вызовов в `POST /api/campaign/:id/turn` (и в `stream`).

| # | Шаг | Кто вызывает | Что происходит |
|---|---|---|---|
| 1 | Валидация ввода | `server.ts` | пусто → 400; длина > 1200 → 400 |
| 2 | Получение сессии | `getSession()` | из памяти или из `data/campaigns/<id>.json`; подставляется ядро, нормализуется состояние, восстанавливаются снимки |
| 3 | Сборка контекста | `runTurn()` → `buildContext()` | сообщения по слоям, сегменты с хешами, `totalTokens` |
| 4 | Кэш-префикс | `cachedPrefix(prev, next)` | сравнение с сегментами прошлого хода до первого расхождения |
| 5 | Вызов ведущего | `model.complete()` или `model.stream()` | структурированный вывод — только если state-агент выключен |
| 6 | Разбор ответа | `parseDelta()` или `reply.delta` | проза отдельно, дельта отдельно; битый JSON — ошибка в `problems`, ход продолжается |
| 7 | Инкремент хода | `runTurn()` | `state.turn += 1` **до** применения дельты |
| 8 | Применение дельты | `applyDelta()` | журнал изменений; отброшенное помечается строкой «отброшено: …» |
| 9 | Критик | `critique()` | вердикт с проблемами; ход не отменяется |
| 10 | Запись лога | `runTurn()` | две записи: `player` (ввод) и `gm` (проза), одинаковый `turn` |
| 11 | State-агент и суммаризатор | `afterTurn()` → `Promise.allSettled` | параллельно, каждый — отдельный вызов модели; падение не отменяет ход |
| 12 | Снимок и диск | `saveSnapshot()`, `persist()` | снимок хода; файл кампании перезаписывается целиком |
| 13 | Ответ | `server.ts` | проза, `changes`, `agentChanges`, `state`, `map`, `worldMap`, `totals`, `usage`, `stats` |

Важно: контекст собирается до применения дельты, поэтому в блоке состояния стоит номер
прошлого хода, а не текущего. Это осознанно: кэш и отчётность считаются по тому, что реально
уходило в модель.

## 4. Формат данных между слоями

### 4.1. Состояние (`GameState`)

20 полей верхнего уровня: `turn`, `time{day,hour}`, `place`, `weather`,
`hero{name,health,wounds,conditions,statuses,card?}`, `money{gold,silver,copper}`,
`items[]`, `party[]`, `npcs[]`, `quests[]`, `promises[]`, `hooks[]`, `factions[]`,
`locations[]`, `archive[]`, `bestiary[]`, `illustrations[]`, `hiddenFacts[]`, `flags{}`, `log[]`.

| Поле | Формат | Смысл |
|---|---|---|
| `hero.health` | число, при применении дельты зажимается в 0..150 | 0 — смерть |
| `hero.wounds[]` | `{where, severity 1..3, treated}` | рана в то же место углубляется, не дублируется |
| `items[]` | `{name, qty, where: equipped\|inventory\|vault\|lost, note?, card?}` | место нахождения — часть предмета |
| `party[]`, `npcs[]` | `{name, role, status: alive\|dead\|gone, bond 0..100, attitude −100..100, present, wounds, appearance?, character?, clothes?, bio?, relations?, card?, portrait?}` | пати и знакомые устроены одинаково |
| `quests[]` | `{title, status: active\|done\|failed\|frozen, steps[], deadline?, createdTurn?, turnsLimit?}` | срок в ходах, просрочка закрывает задачу |
| `archive[]` | `{kind: hook\|promise\|quest\|item, text, turn, reason}` | закрытые страницы истории |
| `hiddenFacts[]` | `{id, turn, content, known}` | факт, зафиксированный до того, как стал важен |
| `log[]` | `{turn, role: player\|gm\|system, text}` | источник истины для истории и конспекта |

### 4.2. Дельта (`Delta`)

Поля: `place`, `weather`, `advanceHours`, `health`, `money`, `addItems[]`, `removeItems[]`,
`conditions[]`, `statuses[]`, `statusRemove[]`, `wounds[]`, `flags{}`, `promises[]`,
`hiddenFacts[]`, `quests[]`, `npcs[]`, `party[]`, `factions[]`, `places[]`, `hooks[]`,
`resolveHooks[]`, `resolvePromises[]`, `archive[]`, `bestiary[]`.

Семантика: `money` — **абсолютные** значения, не приращения; `advanceHours` — приращение времени;
`addItems[].where` нормализуется из свободного текста («карман» → `inventory`).

### 4.3. Ответ модели (`ModelReply`)

```ts
{ text: string; delta?: Delta | null; outputTokens: number;
  inputTokens?: number; cachedTokens?: number }
```

`delta` заполнен только при структурном выводе и только если провайдер вернул JSON с полем
`delta`; иначе `undefined`, и движок идёт через `parseDelta()`.

### 4.4. Сегмент контекста (`Segment`)

```ts
{ name: string; chars: number; tokens: number; hash: string }
```

`tokens = ceil(chars / 3.2)`, `hash` — первые 12 hex-символов SHA-1 от текста. Имена сегментов:
`static`, `conspect.frozen`, `log:<turn>:<role>`, `conspect`, `state`, `turn`.

### 4.5. Результат хода (`TurnStats`)

`turn`, `tokensIn`, `tokensOut`, `cachedTokens`, `cost`, `problems[]`, `changes[]`,
`segments[]` (каждый сегмент + флаг `cached`).

## 5. Где хранится состояние

| Что | Где | Время жизни |
|---|---|---|
| Рабочая сессия (объект `Session`) | память процесса, `Map<id, Session>` в `server.ts` | до перезапуска сервера или сброса глобальных настроек агентов |
| Состояние, конспект, тексты, счётчики, снимки, агенты кампании | `data/campaigns/<id>.json` | постоянно; перезапись целиком после каждого хода |
| Глобальные настройки агентов | `data/agents.json` | постоянно; копия уходит в каждую новую кампанию |
| Ядро правил | `data/source/core.md` (~193 КБ) | читается при загрузке; в файл кампании не пишется, если больше 50 000 знаков |
| Иллюстрации | `data/images/<id>-<timestamp>-<kind>.png` | постоянно, отдаются по `/api/images/<file>` |
| Выбор тегов иллюстратора | `data/art-selection.json` | глобально, не по кампании |

Файл кампании (`SavedCampaign`, версия 1):

```
{ version: 1, savedAt, text{core,world,tone,hero},
  state, conspect: Arc[], summary, usage{}, totals{},
  initial: TurnVariant, turns: TurnSnapshot[], agents{}, meta{} }
```

`TurnSnapshot = {turn, input, prose, state, summary, variants?[]}`,
`TurnVariant = {prose, state, summary}`. Держатся последние 120 снимков, у снимка не больше
4 вариантов. `initial` — состояние до первого хода, точка полного отката.

## 6. Конспект: две формы, одна из них не работает

| Форма | Модуль | Как обновляется | Где в контексте |
|---|---|---|---|
| Арки (append-only) | [`Conspect`](../../../PRG/src/core/conspect.ts#L16) | `openArc()` закрывает предыдущую, `addLine()` только дописывает в последнюю | `conspectFrozen` — закрытые арки; `renderRecent()` в контекст не идёт |
| Скользящий пересказ (`summary`) | [`runSummary()`](../../../PRG/src/server.ts#L159) | каждый ход: прошлый конспект + новый ход → новый текст, обрезка до 6000 знаков | блок `КОНСПЕКТ ПРОШЛОГО:` между историей и состоянием |

```
append-only арки

  ## Арка 1   closed=true   ← заморожена навсегда
  ## Арка 2   closed=true   ← заморожена навсегда
  ## Арка 3   closed=false  ← растёт, дописывается строками

скользящий пересказ

  summary₀ → summary₁ → summary₂ → …   каждый шаг переписывает предыдущий
```

Почему append-only: пересказ пересказа деградирует — детали обрастают подробностями, которых
не было, а однократные факты исчезают. Почему вторая форма всё равно появилась: append-only
арки не покрывают окно последних ходов и не дают «сжатого смысла» для модели.

Статус в PRG: `Conspect` реализован и сохраняется в файл, но в рабочем цикле не наполняется.
`getSession()` ставит `quietConspect = agents.summarizer.enabled`; при включённом
суммаризаторе `runTurn()` не вызывает `addLine()`/`openArc()`. В сохранённой кампании
`conspect` — пустой массив, а память целиком лежит в `summary`. Арки оживают только если
суммаризатор выключен: тогда `runTurn()` пишет механическую строку на каждый ход и открывает
новую арку каждые 10 ходов (`summarizeEvery`).

## 7. Как собирается контекст для модели

Порядок сообщений (`buildContext()`, фактический):

```
1. system : ядро + "\n\n" + мир + "\n\n" + тон + "\n\n" + герой   [static]
2. system : закрытые арки конспекта                              [conspect.frozen]
3. user/assistant × N : последние ходы из state.log              [history]
4. system : "КОНСПЕКТ ПРОШЛОГО:\n" + summary                     [conspect]
5. system : renderState(state)                                   [state]
6. user   : ввод игрока                                          [turn]
```

Правила:

- Пустые блоки не добавляются: если `conspectFrozen` пуст, сообщения и сегмента нет.
- История — настоящие сообщения: `player` → `user`, `gm` и `system` → `assistant`.
- Окно: `windowSize = windowTurns * 2` сообщений (30 ходов → 60 сообщений).
  `start = all.length <= windowSize ? 0 : floor((all.length - windowSize) / 20) * 20`.
  Сдвиг происходит блоками по 20 сообщений (10 ходов), а не по одному: иначе первый элемент
  окна менялся бы каждый ход, префикс рассыпался и кэш умирал бы ровно на длинной истории.
- Состояние стоит после истории и после конспекта, потому что меняется каждый ход.
- `renderState()` обрезает длинные списки: крючки — последние 12, места — 8, бестиарий — 8,
  архив — 12; полные списки живут в панели клиента.
- `cachedPrefix()` складывает токены сегментов, совпавших по хешу с прошлым ходом, и
  останавливается на первом расхождении. Это оценка попадания в кэш для отчётности; если
  провайдер вернул `cached_tokens`, берётся его число.

## 8. Роль критика

Критик — не оценка качества прозы. Это проверка на поломки, из-за которых сессия «плывёт»:

| Проверка | Порог | Проблема |
|---|---|---|
| Пустой ответ | `prose.trim()` пуст | «пустой ответ» |
| Нет дельты | `expectDelta === true` и `delta === null` | «нет блока изменений — стейт не обновится» |
| Объём | > 2500 символов | «перебор объёма» |
| Объём | > 0 и < 60 символов | «слишком короткий ответ» |
| Вопрос игроку | регулярные выражения «что будешь делать?», «твой ход?», «что дальше?», «как поступишь?» | «вопрос игроку вместо ведения — нарушена граница хода» |
| Подталкивание | «тебе решать», «ты решаешь», «решение за тобой», «выбор за тобой», «тебе выбирать» | «подталкивание к решению вместо паузы» |
| Скрытые факты | больше 2 за ход | «скрытых фактов за ход: N (норма ≤ 2)» |
| Предмет без изменений | в прозе «берёшь/поднимаешь/кладёшь/снимаешь/отдаёшь/прячешь», `changes` пуст | «в сцене действие с предметом, но изменений в стейте нет» |

Вердикт `{ok, problems[]}` возвращается в `TurnStats.problems` и доезжает до клиента, где
показывается в строке метаданных ответа. Критик не отменяет ход, не вызывает модель повторно
и не правит состояние. Аргумент `state` в `critique()` не используется (`void state`) —
задел под будущие сверки.

## 9. Где менять, если добавляешь механику

| Задача | Точка изменения |
|---|---|
| Новое поле состояния | `GameState` + `createState()` + `normalizeState()` + `renderState()` + панель клиента |
| Новый вид изменения | `Delta` + ветка в `applyDelta()` + (при структурном выводе) `TURN_SCHEMA` в `openrouter.ts` |
| Новое правило критика | `critic.ts`, массив проверок; без обращения к модели |
| Новый слой контекста | `ContextInput` + `buildContext()`; место в порядке выбирается по стабильности |
| Новая роль агента | `AgentId` + `DEFAULT_AGENTS` + вызов в `server.ts` |
| Новая операция над кампанией | ветка `action === '…'` в маршруте `/api/campaign/:id/*` |

## 10. Честный статус (по коду, не по документации)

| Утверждение из docs | Фактическое состояние в коде |
|---|---|
| «Конспект append-only, закрытые арки не переписываются» | Класс есть, но в рабочем цикле арки не наполняются; память — переписываемый `summary` |
| «Критик: провал → один ретрай» | Ретрая нет ни в `runTurn()`, ни в `server.ts`; проблемы только репортятся |
| «История — последние 30 ходов, остальное в конспекте» | Окно 30 ходов есть, но `summary` пересказывает **всю** историю, включая эти 30 ходов: свежие события дублируются в двух блоках |
| «Суммаризатор раз в N сообщений» | `runSummary()` вызывается на каждом ходу; поле `everyMessages` показывается в UI, но сервером не читается |
| «У каждой игры свои агенты» | Для `gm`/`state`/`summarizer` — да; иллюстраторы берутся из глобальных настроек, `POST /api/agents/:id/test` тоже тестирует глобального агента |
| «Стоимость хода считается по модели» | Цены берутся один раз для `MODEL` (переменная окружения); агенты на других моделях считаются по этим же ценам |
| «Смена настроек агента применяется к игре» | `expectDelta`, `quietConspect` и структурированность модели фиксируются при создании сессии; переключение `enabled` в середине игры начинает действовать только после перезагрузки сессии |
| «Схема ответа описывает изменения» | `TURN_SCHEMA` уже, чем `Delta`: в ней нет `npcs`, `party`, `quests`, `statuses`, `factions`, `places`, `resolveHooks`, `resolvePromises`, `archive`, `bestiary` |
| `ROADMAP.md`: M0 закрыт, есть `src/demo.ts` и `src/play.ts` | Файлов нет; CLI-цикла нет |
| Библия собирается «за один вызов» из тегов | `src/start/assemble.ts` — каркас, сервером не вызывается; сборка идёт через `/api/generate/tone`, `/api/generate/world` и `/api/campaigns` |
| `README.md`: таблица API | Нет `/api/art-tags` (GET/PUT) и `/api/images/<file>`; у `/image` указаны только `scene`/`portrait`, в коде ещё `card`, `item`, `hero` |
| «Порядок: статика → история → конспект → состояние» (README) | Фактически: статика → закрытые арки → история → конспект прошлого → состояние → ход |

Дополнительно к этому списку: нет блокировки сессии (два одновременных хода на одну кампанию
могут перетереть состояние), нет таймаута и отмены для текстовых вызовов модели (только для
иллюстраций — 120 с), `money` можно завысить (валидируется только минус и обнуление),
`advanceHours` не округляется до целого, `severity` новой раны не проверяется, а у клиента
остались неиспользуемые остатки каталога миров (`TEMPLATES`, `viewCatalog`, `viewCatalog2`).

## 11. Быстрый индекс для исполнителя

1. `core/state.ts` — схема; менять только вместе с `renderState()` и панелью.
2. `core/delta.ts` — единственное место, где меняется состояние; всё остальное только читает.
3. `core/context.ts` — единственное место, где определяется порядок и объём контекста.
4. `core/turn.ts` — единственное место, где определяется порядок шагов хода.
5. `server.ts` — единственное место, где сессии, снимки, файлы и HTTP.
6. `web/app.js` — единственное место, где рендер и действия игрока.
