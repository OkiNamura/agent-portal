# 02. Спецификация для воспроизведения

Документ описывает, что именно должно быть построено, в терминах проверяемых утверждений.
Он не пересказывает PRG: там, где PRG расходится с требуемым поведением, это указано явно.

**Как читать.**

- Блок = одна замкнутая область ответственности с собственными входами и выходами.
- «Статус в PRG»: *реализовано* — поведение есть и работает; *частично* — код есть, но
  в рабочем цикле не применяется или покрывает не всё; *отсутствует* — в PRG нет.
- Критерий приёмки — утверждение, которое проверяется юнит-тестом, интеграционным тестом
  или явным действием в браузере. Оценочные формулировки без проверяемого смысла
  в критериях не используются.
- Пометка **(сверх PRG)** означает требование, которого в PRG нет; его нужно реализовать,
  чтобы блок считался принятым.
- Числа (лимиты, пороги) — часть контракта. Менять их можно только вместе с критериями.

**Общие соглашения.**

- Язык прозы и интерфейса — русский; оценка токенов — 3,2 символа на токен.
- Время — `{day, hour}`, час целый 0..23; деньги — три номинала, значения неотрицательные.
- Все структуры сериализуются в JSON без циклических ссылок и без `undefined` в файле.
- «Ход» нумеруется с 1; состояние до первого хода имеет `turn = 0`.

## Блок 1. Состояние кампании

**Статус в PRG:** реализовано полностью.

**Цель.** Типизированный JSON — единственный источник правды о цифрах; проза не является
носителем состояния.

**Входы.** Имя героя, стартовое место.

**Выходы.** Объект `GameState` с 20 полями верхнего уровня; нормализованная копия для старых
сохранений; глубокая копия; запись скрытого факта.

**Поведение.**

- Новая игра начинается с `turn = 0`, `time = {day: 1, hour: 8}`, `weather = "холодный туман"`,
  `health = 100`, денег `{gold: 0, silver: 12, copper: 40}`, пяти надетых предметов.
- Загрузка старого файла дополняет отсутствующие массивы и объекты, не затирая существующие.
- Копия состояния не разделяет вложенные объекты с оригиналом.
- Скрытый факт получает уникальный id вида `hf-<turn>-<n>` и флаг `known: false`.

**Критерии приёмки.**

- **C1.1** `createState('Кай', 'Площадь')` возвращает `turn = 0`, `time.day = 1`, `time.hour = 8`,
  `weather = 'холодный туман'`, `hero.health = 100`, `money = {gold:0, silver:12, copper:40}`.
- **C1.2** `createState` даёт ровно 5 предметов, у всех `where = 'equipped'`: кинжал-стилет,
  плащ шерстяной, рубаха льняная, сапоги кожаные, ремень с кошелём.
- **C1.3** `createState` содержит ровно 20 ключей верхнего уровня, включая пустые `log: []`,
  `flags: {}`, `archive: []`, `hiddenFacts: []`.
- **C1.4** `normalizeState` на объекте без `items`, `npcs`, `log`, `hero.wounds` добавляет
  пустые массивы, не бросает исключение и оставляет `hero.health = 100`, если поля не было.
- **C1.5** `normalizeState` не затирает данные: состояние с одним предметом и одним NPC
  сохраняет их количество и содержимое после нормализации.
- **C1.6** После `cloneState` добавление предмета в копию не меняет `items` оригинала
  (длина оригинала прежняя).
- **C1.7** `addHiddenFact(state, 'засада')` увеличивает `hiddenFacts` на 1, даёт `turn`, равный
  `state.turn`, `known = false` и id, соответствующий `/^hf-\d+-\d+$/`; второй вызов даёт другой id.
- **C1.8** Изменение `state.hero.health` в копии не отражается на оригинале (проверка глубокого
  копирования вложенного объекта).

**Инварианты.**

- В состоянии нет полей, которые нельзя проверить: всё, что не проверяется, остаётся в прозе.
- Нормализация идемпотентна: повторный вызов не меняет объект.
- Копия состояния не имеет общих ссылок с оригиналом.

**Что НЕ входит.** Миграции с изменением смысла полей, версионирование схемы внутри кампании,
хранение в базе данных, шифрование файла.

## Блок 2. Хранилище и снимки

**Статус в PRG:** реализовано; ограничение — нет миграции версии и нет блокировки файла.

**Цель.** Один JSON на кампанию; по снимку на каждый ход как основа откатов и веток.

**Входы.** Каталог кампаний, id, объект кампании; для загрузки — каталог и id.

**Выходы.** Файл `data/campaigns/<id>.json`; при загрузке — объект или `null`; снимки ходов
в памяти и в файле.

**Поведение.**

- Запись добавляет `version: 1` и `savedAt` в ISO 8601, создаёт каталог при отсутствии,
  пишет JSON с отступом 2 и завершающим переводом строки.
- Загрузка возвращает `null` при отсутствии файла, битом JSON и версии, отличной от 1.
- Снимок хода: `{turn, input, prose, state, summary, variants?}`; снимок заменяет прежний
  снимок того же хода.
- Хранятся последние 120 снимков; у снимка не больше 4 вариантов.
- `initial` — состояние до первого хода, с пустым логом.

**Критерии приёмки.**

- **C2.1** После сохранения файл существует, парсится как JSON, содержит `version = 1`
  и `savedAt`, соответствующий ISO 8601.
- **C2.2** Круговой рейс: `loadCampaign(saveCampaign(x))` даёт равные `state`, `conspect`,
  `summary`, `totals`, `meta` (кроме `savedAt`).
- **C2.3** `loadCampaign` для несуществующего id возвращает `null` без исключения.
- **C2.4** Файл с текстом `{` вместо JSON: `loadCampaign` возвращает `null` без исключения.
- **C2.5** Файл с `version: 2` возвращает `null`.
- **C2.6** После добавления 130 снимков в кампании остаётся 120, последний снимок присутствует,
  первый отброшен.
- **C2.7** Снимок содержит обязательные поля `turn`, `input`, `prose`, `state`, `summary`;
  число вариантов не превышает 4.
- **C2.8** `initial.state.turn = 0`, `initial.state.log = []`, а `initial.prose = ''`.
- **C2.9** Второе сохранение полностью заменяет первое: после двух записей подряд файл
  содержит состояние второго вызова, а не смесь первого и второго (проверка по маркеру
  в `place` и по длине `log`).

**Инварианты.**

- Сохранение перезаписывает файл целиком; частично записанных кампаний не бывает.
- Снимок хода неизменяем после записи, кроме замены самого снимка при перегенерации.
- Файл читается человеком: отступы, отсутствие минификации.
- Снимки хранят и состояние, и конспект: откат восстанавливает оба.

**Что НЕ входит.** Транзакции, блокировки файла, сжатие, база данных, миграции старых версий,
хранение нескольких кампаний в одном файле.

## Блок 3. Разбор ответа модели (дельта из текста)

**Статус в PRG:** реализовано.

**Цель.** Отделить прозу от блока изменений, если провайдер не умеет структурный вывод.

**Входы.** Сырой текст ответа модели.

**Выходы.** `{prose, delta | null, error?}`.

**Поведение.**

- Ищутся все огороженные блоки с языком `json`; берётся последний.
- Проза — весь текст за вычетом последнего блока, обрезанный по краям.
- Если блоков нет — вся строка считается прозой, дельта `null`.
- Битый JSON — дельта `null`, проза сохранена, в `error` строка «не разобрал JSON: …».
- Блок с другим языком или без языка дельтой не считается.
- При структурном выводе разбор не выполняется: проза и дельта приходят полями.

**Критерии приёмки.**

- **C3.1** Вход: строка `текст`, затем блок с языком `json` и телом `{"advanceHours":1}` —
  результат: проза `текст`, `delta.advanceHours = 1`, `error` отсутствует.
- **C3.2** Вход без блока даёт прозу, равную исходной строке без крайних пробелов,
  `delta = null`, `error` отсутствует.
- **C3.3** При двух блоках берётся последний: проза содержит текст первого блока как обычный
  текст, дельта равна содержимому второго.
- **C3.4** Битый JSON (`{"advanceHours":`) даёт `delta = null`, прозу без блока и `error`,
  начинающийся с «не разобрал JSON».
- **C3.5** Блок с языком `text` или без языка не распознаётся: дельта `null`, блок остаётся
  в прозе.- **C3.6** При структурном ответе с `delta = {}` проза равна `text.trim()`, дельта `{}`,
  повторный парсинг не выполняется.

**Инварианты.**

- Разбор никогда не бросает исключение.
- Проза и дельта не пересекаются: блок изменений не остаётся в тексте для игрока.
- Отсутствие дельты — не ошибка разбора; это отдельное состояние.

**Что НЕ входит.** Восстановление обрезанного JSON, несколько дельт за ход, JSON без блока
(чистый объект вместо прозы), исправление опечаток модели.

## Блок 4. Применение дельты и валидация

**Статус в PRG:** реализовано; отдельные поля валидируются частично (указано в критериях).

**Цель.** Модель предлагает — движок применяет. Непрошедшее изменение отбрасывается,
ход продолжается, журнал изменений показывает и применённое, и отброшенное.

**Входы.** `GameState` (мутируется), `Delta`.

**Выходы.** Массив человекочитаемых строк изменений.

**Поведение.**

- Время: `advanceHours > 0` прибавляется с переносом суток; ноль и минус игнорируются.
- Место и погода применяются только непустой строкой после обрезки пробелов.
- Деньги — абсолютные значения; отрицательные номиналы отбрасываются; полное обнуление
  кошеля при ненулевом остатке отбрасывается как «обнуление без причины».
- Предметы: добавление сливается с существующим по имени без учёта регистра; удаление
  несуществующего отбрасывается; при количестве ≤ 0 запись удаляется.
- Место нахождения предмета нормализуется из свободного текста.
- Раны: рана в то же место (без учёта регистра) углубляется на 1, максимум 3, `treated = false`.
- Здоровье зажимается в 0..150.
- Эффекты: добавление по имени, обновление вида и заметки, снятие по имени.
- Обещания: нормализация формы («обещание:», «обещаю», «клянусь») и дедупликация;
  служебные метки вида `promise_2` отбрасываются; закрытые уходят в архив.
- Задачи: создание с `createdTurn`, обновление статуса, шагов, срока; `done`/`failed` уходят
  в архив; просрочка (`turn − createdTurn > turnsLimit`) закрывает задачу, пишет архив
  и добавляет крючок «Просрочено: …».
- NPC: безличные описания («некто», «женщина», «голос», «силуэт») отбрасываются; один и тот же
  персонаж под именем и прозвищем не дублируется; хранятся последние 60.
- Пати: та же карточка, что и у NPC, но без фильтра безличности.
- Фракции: отношение зажимается в −100..100, дубликаты обновляются.
- Места: хранятся последние 40.
- Крючки: дубликаты не добавляются; при превышении 60 активных старые уходят в архив
  с причиной «вытеснен»; закрытые — с причиной «закрыт».
- Архив: дубликаты по паре «вид + текст» не добавляются.
- Бестиарий: дубликаты по имени обновляются.
- Скрытые факты: каждый элемент дельты создаёт запись через `addHiddenFact`.
- Флаги: значения перезаписываются по ключу.

**Критерии приёмки.**

- **C4.1** При `time = {day:1, hour:8}` дельта `{advanceHours: 3}` даёт `11:00`;
  `{advanceHours: 20}` даёт `{day:2, hour:4}`.
- **C4.2** Дельты `{advanceHours: 0}` и `{advanceHours: -5}` не меняют `time`.
- **C4.3** `{place: '  Таверна  '}` даёт `place = 'Таверна'`; `{place: '   '}` не меняет место.
- **C4.4** `{money: {gold: -1}}` не меняет золото, а журнал содержит «отброшено: gold < 0»;
  `{money: {gold:0, silver:0, copper:0}}` при сумме 52 отбрасывается целиком.
- **C4.5** Добавление «камень» ×1, затем «Камень» ×2 даёт ровно одну запись с `qty = 3`.
- **C4.6** Удаление отсутствующего предмета не меняет `items`, журнал содержит
  «отброшено: нет предмета «нож»».
- **C4.7** `where`: «карман» → `inventory`, «в руках» → `equipped`, «схрон» → `vault`,
  пустая строка → `inventory`.
- **C4.8** Раны «левое плечо» (severity 1), затем «Левое плечо» (severity 2), затем снова:
  одна запись, severity 3, `treated = false`.
- **C4.9** `{health: -20}` даёт 0; `{health: 999}` даёт 150; `{health: 55}` даёт 55.
- **C4.10** NPC «некто», «Голос из темноты», «Женщина у очага» отброшены; «Капюшон»
  и «Гуннар» добавлены; при 61 именованном NPC в состоянии остаётся 60.
- **C4.11** Задача с `turnsLimit: 2`, созданная на ходу 0, при `state.turn = 3` получает
  статус `failed`, запись в архиве с причиной «просрочено» и крючок, начинающийся с «Просрочено».
- **C4.12** «обещаю вернуться с подмогой» и «Обещание: обещаю вернуться с подмогой» дают
  одно обещание; `resolvePromises` переносит его в архив с причиной «выполнено или снято».
- **C4.13** 61 активный крючок оставляет 60 активных, а вытесненный попадает в архив
  с причиной «вытеснен»; `resolveHooks` даёт причину «закрыт».
- **C4.14** `{factions:[{name:'Гильдия', attitude:-150}]}` даёт −100; повторная запись
  «гильдия» обновляет существующую, а не создаёт вторую; 41 место оставляет 40.
- **C4.15** Два скрытых факта за один вызов дают две записи в `hiddenFacts` с разными id
  и `turn`, равным текущему.
- **C4.16** Флаги `{flags:{a:true}}`, затем `{flags:{a:false}}` дают `a = false`; повторная
  запись того же архива (вид + текст) не увеличивает `archive`.

**Инварианты.**

- Чего нет в дельте — того не было: непришедшие поля состояния не меняются.
- Ни одно изменение дельты не бросает исключение и не прерывает ход.
- Одно и то же имя в разных регистрах — одна сущность (предмет, NPC, фракция, место, задача).
- Удалённое из активных списков не исчезает из истории: крючки, обещания, задачи и предметы
  при закрытии попадают в архив.
- Журнал изменений отражает и применённое, и отброшенное; отброшенное начинается со слова
  «отброшено».
- Деньги не могут стать отрицательными; здоровье не выходит за 0..150; отношения — за −100..100.

**Что НЕ входит.** Проверка, что изменение описано в прозе (кроме одного правила критика);
пересчёт производных величин; откат части применённой дельты при ошибке в середине; валидация
`severity` новой раны (в PRG не проверяется; по схеме допустимо 1..3 — при реализации
это надо проверять); округление дробных `advanceHours` (в PRG не реализовано — час должен
быть целым).

## Блок 5. Конспект: арки append-only

**Статус в PRG:** частично — модуль реализован и сохраняется, но в рабочем цикле не наполняется
(см. блок 6 и `01-architecture.md`, раздел «Честный статус»).

**Цель.** Память о старом не перегенерируется: закрытая арка заморожена навсегда, открытая
только дописывается.

**Входы.** Заголовок конспекта; вызовы «открыть арку», «дописать строку»; сохранённый массив арок.

**Выходы.** Два рендера: закрытые арки с заголовком и текущая арка; сериализация и восстановление.

**Поведение.**

- Открытие новой арки закрывает предыдущую открытую и добавляет новую с пустым телом.
- Дописывание работает только с последней аркой; при отсутствии арок создаётся «Арка 1».
- Рендер закрытого содержит заголовок конспекта и все закрытые арки; пустой результат, если
  закрытых нет.
- Рендер текущего содержит одну открытую арку с пометкой «(текущая)».
- Восстановление из JSON делает глубокую копию: правка восстановленного не меняет исходный массив.

**Критерии приёмки.**

- **C5.1** Новый конспект: `arcCount = 0`, `closedCount = 0`, `renderFrozen() = ''`,
  `renderRecent() = ''`.
- **C5.2** `addLine('строка')` на пустом конспекте создаёт арку «Арка 1» с телом «строка».
- **C5.3** После `openArc('Арка 1'); openArc('Арка 2')` имеем `arcCount = 2`, `closedCount = 1`.
- **C5.4** Тело «Арка 1», снятое до открытия «Арка 2», побайтово равно телу после 10 дописываний
  в «Арка 2».
- **C5.5** `renderFrozen()` содержит заголовок конспекта, «## Арка 1» и не содержит «Арка 2»,
  пока она открыта.
- **C5.6** `renderRecent()` содержит «## Арка 2 (текущая)» и не содержит «## Арка 1».
- **C5.7** `Conspect.fromJSON(c.toJSON())` даёт равные арки; правка восстановленного объекта
  не меняет исходный.
- **C5.8** Если между двумя соседними ходами арка не открывалась и не закрывалась,
  `renderFrozen()` на этих ходах побайтово равен (стабильность префикса контекста).

**Инварианты.**

- Конспект не перезаписывается: закрытая арка не участвует ни в одной операции записи.
- Порядок арок — порядок открытия; тело арки — конкатенация строк через перевод строки.
- Добавление строки никогда не меняет предыдущие арки.

**Что НЕ входит.** Сжатие нескольких арок в одну, удаление арок, правка тела закрытой арки,
поиск по конспекту, участие текущей арки в контексте (в PRG `renderRecent()` в контекст не идёт).

## Блок 6. Скользящий конспект (`summary`)

**Статус в PRG:** реализовано; пересказывает всю историю, включая окно последних ходов.

**Цель.** Держать смысл всей истории в ограниченном объёме, чтобы контекст не рос
с длиной кампании.

**Входы.** Предыдущий `summary`, ввод игрока, проза ведущего.

**Выходы.** Новый `summary` (≤ 6000 знаков), отметка хода последнего обновления.

**Поведение.**

- Каждый ход агент получает прошлый конспект, новый ввод и прозу, возвращает обновлённый текст.
- Префикс «КОНСПЕКТ:» срезается; пустой ответ не заменяет прежний конспект.
- Результат обрезается до 6000 знаков; в контекст идёт блоком «КОНСПЕКТ ПРОШЛОГО:».
- При выключенном агенте конспект не меняется, ход продолжается.
- Ошибка агента не отменяет ход и не меняет конспект.
- Конспект входит в снимок хода, поэтому откат восстанавливает и его.

**Критерии приёмки.**

- **C6.1** При пустом прежнем конспекте запрос к агенту содержит строку «(пусто)».
- **C6.2** Ответ «КОНСПЕКТ: текст» даёт `summary = 'текст'`.
- **C6.3** Ответ длиной 7000 знаков даёт `summary` длиной 6000.
- **C6.4** При `enabled = false` у суммаризатора `summary` не меняется, результат
  `{ok: false}`, ход сохраняется.
- **C6.5** После перезапуска сервера `summary` из файла кампании равен конспекту после
  последнего успешного хода.
- **C6.6** В собранном контексте блок «КОНСПЕКТ ПРОШЛОГО: …» стоит после сообщений истории
  и до блока состояния.
- **C6.7** Ошибка вызова суммаризатора не меняет код ответа хода: ответ 200, `summary`
  прежний, в лог сервера пишется сообщение об ошибке.
- **C6.8** Откат к снимку хода N восстанавливает `summary`, равный значению в этом снимке.

**Инварианты.**

- Конспект — производное от лога: он никогда не является источником истины.
- Объём конспекта ограничен 6000 знаками независимо от длины кампании.
- Сбой конспектировщика не влияет на состояние, лог и ответ игроку.
- Конспект не содержит служебных заголовков и пояснений агента.

**Что НЕ входит.** Ограничение конспекта окном («всё старше N ходов»), поиск по конспекту,
несколько уровней сжатия, ручная правка конспекта игроком.

## Блок 7. Сборка контекста

**Статус в PRG:** реализовано.

**Цель.** Собрать сообщения в порядке от самого стабильного к самому изменчивому, чтобы
префикс запроса попадал в кэш провайдера, и показать состав контекста сегментами.

**Входы.** Ядро, мир, тон, герой, закрытые арки, скользящий конспект, состояние, число ходов
окна, ввод игрока.

**Выходы.** `messages[]` для провайдера, `segments[]`, `totalTokens`.

**Поведение.**

- Порядок: `static` → `conspect.frozen` → история → `conspect` → `state` → `turn`.
- `static` — конкатенация непустых блоков через два перевода строки.
- История — сообщения из лога: `player` → `user`, `gm` и `system` → `assistant`.
- Окно — `windowTurns * 2` сообщений; сдвиг кратными блоками по 20 сообщений.
- Каждый сегмент: имя, длина, оценка токенов, хеш; `totalTokens` — сумма.
- Пустые блоки (арки, конспект) не добавляются вовсе.

**Критерии приёмки.**

- **C7.1** При непустых всех блоках роли сообщений идут в порядке: `system, system,
  user/assistant…, system, system, user`; первый — статика, последний — ввод игрока.
- **C7.2** `static` равен `core + '\n\n' + world + '\n\n' + tone + '\n\n' + hero`;
  пустой `hero` не оставляет лишних переводов строки в конце.
- **C7.3** Лог из 80 сообщений при `windowTurns = 30` даёт окно из 60 сообщений, начинающееся
  с индекса 20; лог из 79 сообщений даёт окно из 79 сообщений (сдвиг ещё не произошёл).
- **C7.4** Лог 80 и 81 сообщение дают одинаковое начало окна (индекс 20): сдвиг на одно
  сообщение не меняет префикс.
- **C7.5** Имена сегментов: `static`, `conspect.frozen`, `log:<turn>:<role>`, `conspect`,
  `state`, `turn`; у каждого `chars` равно длине текста, `tokens = ceil(chars / 3.2)`,
  `hash` — 12 hex-символов.
- **C7.6** `cachedPrefix` при полном совпадении сегментов возвращает сумму их токенов;
  при расхождении на третьем сегменте — сумму первых двух; при пустом прошлом списке — 0.
- **C7.7** `renderState` содержит строки «ТЕКУЩЕЕ СОСТОЯНИЕ (ход N)», «Время: день D, HH:00»,
  «Место: …», «Погода: …», «Раны: …», «Состояния: …», «Здоровье: …», «Деньги: …»,
  «Предметы: …».
- **C7.8** `renderState` при 20 крючках выводит только последние 12; при 12 местах — 8;
  при 12 существах — 8; при 20 записях архива — 12.
- **C7.9** Запись лога с ролью `system` попадает в сообщение с ролью `assistant`.
- **C7.10** `totalTokens` равен сумме `tokens` всех сегментов.
- **C7.11** Пустые `conspectFrozen` и `summary` не добавляют сообщений и сегментов:
  количество сообщений уменьшается ровно на пропущенные блоки.
- **C7.12** Два вызова `buildContext` с одинаковыми входами дают одинаковые хеши сегментов
  (детерминированность).

**Инварианты.**

- Порядок слоёв фиксирован; изменение порядка — изменение контракта кэша.
- Динамические блоки (состояние, ввод) стоят после истории и не ломают её префикс.
- Любой сегмент имеет уникальное имя в пределах одного контекста.
- Оценка токенов — приблизительная и не зависит от провайдера.

**Что НЕ входит.** Точная токенизация моделью, обрезка по жёсткому лимиту контекста,
несколько вариантов сборки, эмбеддинги и поиск по истории.

## Блок 8. Вызов модели, структурный вывод и стрим

**Статус в PRG:** реализовано; нет таймаута и отмены, нет повторов на 429/5xx.

**Цель.** Спрятать провайдера за интерфейсом `Model`: движок не знает, локальная это модель,
OpenRouter или мок.

**Входы.** Массив сообщений, лимит токенов, конфигурация агента.

**Выходы.** `ModelReply {text, delta?, outputTokens, inputTokens?, cachedTokens?}`.

**Поведение.**

- Структурный вывод: запрос с `response_format` типа `json_schema`, имя схемы `turn`,
  обязательные поля `prose` и `delta`.
- Если провайдер отклонил структурированный запрос, выполняется один повтор без схемы.
- `reasoning` по умолчанию выключен; при включении — параметр в теле запроса.
- `max_tokens`: 1200 для структурного, 900 для обычного, если лимит не задан агентом.
- Ответ провайдера может содержать JSON в любом месте строки: извлекается объект от первой `{`
  до последней `}`; проза — текст до объекта, дельта — поле `delta` или `{}`.
- Стрим читает SSE-кадры `data: …`, склеивает куски, отдаёт их через колбэк, игнорирует `[DONE]`,
  берёт `usage` из последнего кадра с полем `usage`.
- Цифры usage от провайдера приоритетнее оценки; при отсутствии — оценка по символам
  и кэш-префикс.
- Ошибка провайдера — исключение с текстом, содержащим статус, модель и первые 300 символов тела.

**Критерии приёмки.**

- **C8.1** При `structured = true` тело запроса содержит `response_format.type = 'json_schema'`
  и `response_format.json_schema.name = 'turn'`.
- **C8.2** Если первый структурированный запрос вернул 4xx, выполняется ровно один повтор
  без `response_format`; при успехе второго ответ возвращается как обычный текст.
- **C8.3** При `structured = false` выполняется ровно один запрос, `response_format`
  в теле отсутствует.
- **C8.4** При `reasoning` по умолчанию тело содержит `reasoning.enabled = false`.
- **C8.5** Без явного лимита `max_tokens = 1200` для структурного режима и `900` для обычного;
  явный `maxTokens` переопределяет оба значения.
- **C8.6** Ответ `«проза {"prose":"П","delta":{"advanceHours":1}}»` даёт прозу «проза»
  и дельту `{advanceHours:1}`; строка без поля `prose` даёт `null` (разбор не удался).
- **C8.7** Стрим из кадров с кусками «a», «b», «[DONE]» вызывает колбэк дважды и возвращает
  текст «ab».
- **C8.8** Если ответ содержит `usage.prompt_tokens = 100`, `completion_tokens = 20`,
  `prompt_tokens_details.cached_tokens = 40`, то `inputTokens = 100`, `outputTokens = 20`,
  `cachedTokens = 40`.
- **C8.9** Ответ без `usage` даёт `outputTokens = ceil(len(text) / 3.2)`.
- **C8.10** Ответ 500 от провайдера даёт исключение, текст которого содержит код 500,
  имя модели, а тело ответа обрезано до 300 символов.

**Инварианты.**

- Движок не зависит от провайдера: замена реализации `Model` не меняет `turn.ts`.
- Структурный вывод и текстовый разбор дают одинаковую форму результата.
- Ошибка провайдера не оставляет частично применённого хода.
- Стрим не используется, когда ответ содержит JSON (иначе игрок увидел бы служебный блок).

**Что НЕ входит.** Повторы с backoff, отмена запроса, потоковая передача JSON-дельты,
кэширование ответов, выбор провайдера по цене во время игры, локальные модели.

## Блок 9. Агенты и настройки

**Статус в PRG:** реализовано; `everyMessages` не применяется, иллюстраторы и тест не учитывают
настройки кампании.

**Цель.** Семь ролей с собственными моделью, температурой, лимитом и промтом; у каждой игры
своя копия настроек.

**Входы.** Файл `data/agents.json`, правки через API, кампания для выбора области правки.

**Выходы.** Набор из 7 конфигураций; сохранённый файл; применение к вызовам модели.

**Поведение.**

- Роли: `gm`, `state`, `summarizer`, `artistHero`, `artistNpc`, `artistItem`, `artistScene`.
- По умолчанию включены `gm`, `state`, `summarizer`; иллюстраторы выключены.
- Температура зажимается в 0..2, лимит токенов — в 0..32000; id и title не перезаписываются.
- При создании кампании набор копируется в её файл; правка копии не меняет глобальный файл.
- Отсутствующий или битый глобальный файл заменяется значениями по умолчанию без исключения.
- Сохранение глобальных настроек сбрасывает кэш сессий, чтобы новые значения применились.
- Версия файла настроек — 10; старые версии получают актуальные промты состояния
  и конспектировщика.

**Критерии приёмки.**

- **C9.1** `DEFAULT_AGENTS` содержит ровно 7 ключей с указанными id; у каждого есть `title`,
  `enabled`, `model`, `temperature`, `maxTokens`, `prompt`.
- **C9.2** По умолчанию `gm/state/summarizer.enabled = true`, все `artist*.enabled = false`,
  температура `state` и `summarizer` равна 0,2.
- **C9.3** После создания кампании её `agents` содержит 7 ключей; изменение `agents.json`
  не меняет агентов уже созданной кампании (сравнение до/после).
- **C9.4** `PUT /api/agents/state` с `campaign = <id>` меняет только копию кампании;
  `GET /api/agents` без параметра возвращает прежнюю глобальную конфигурацию.
- **C9.5** `temperature: 5` сохраняется как 2; `temperature: -1` — как 0;
  `maxTokens: 40000` — как 32000; `maxTokens: -5` — как 0.
- **C9.6** При отсутствии `data/agents.json` загрузка возвращает значения по умолчанию
  и не бросает исключение; битый JSON — то же.
- **C9.7** `resetAgent('gm')` возвращает объект, равный `DEFAULT_AGENTS.gm`, и последующая
  правка результата не меняет `DEFAULT_AGENTS`.
- **C9.8** После `saveAgents` файл содержит `version = 10` и `agents` из 7 ключей.

**Инварианты.**

- Глобальные настройки — шаблон; кампания работает на своей копии.
- Правка агента не меняет состояние игры и не запускает ход.
- Значения температуры и лимита всегда в допустимом диапазоне.
- Промт — часть данных, а не кода: его можно заменить без пересборки.

**Что НЕ входит.** Версионирование промтов внутри кампании (в PRG миграция только глобальная),
роли с несколькими моделями на одну задачу, A/B-сравнение моделей, автоматический выбор модели.

## Блок 10. Критик

**Статус в PRG:** реализовано; модель-критик и повтор хода отсутствуют.

**Цель.** Дешёвыми детерминированными правилами ловить поломки хода, из-за которых сессия
«плывёт», и сообщать о них без отмены хода.

**Входы.** Состояние (зарезервировано), проза, дельта, журнал изменений, флаг «дельта ожидается».

**Выходы.** `{ok, problems[]}`.

**Поведение.** Проверки перечислены в таблице `01-architecture.md`, раздел 8; повторяются здесь
как контракт: пустая проза; отсутствие дельты при `expectDelta`; объём > 2500 и < 60 символов;
вопрос игроку; подталкивание к решению; больше 2 скрытых фактов; действие с предметом без
изменений. Каждая проверка добавляет одну строку в `problems`; `ok` истинно только при пустом
списке.

**Критерии приёмки.**

- **C10.1** Пустая проза при непустой дельте даёт `ok = false` и проблему «пустой ответ».
- **C10.2** `expectDelta = true`, `delta = null` даёт проблему «нет блока изменений —
  стейт не обновится».
- **C10.3** Проза 2501 символ даёт «перебор объёма: 2501 символов»; 59 символов — «слишком
  короткий ответ»; 60 символов при непустой дельте дают вердикт без проблем объёма.
- **C10.4** Проза «Что будешь делать?» даёт «вопрос игроку вместо ведения — нарушена граница
  хода»; проза «Тебе решать» даёт «подталкивание к решению вместо паузы».
- **C10.5** Три скрытых факта в дельте дают «скрытых фактов за ход: 3 (норма ≤ 2)».
- **C10.6** Дельта без изменений и проза «берёшь камень со стола» дают «в сцене действие
  с предметом, но изменений в стейте нет».
- **C10.7** При `expectDelta = false` и `delta = null` (проза в норме) вердикт `ok = true`.
- **C10.8** Два вызова с одинаковыми входами дают глубоко равные вердикты (детерминированность,
  без обращения к сети).
- **C10.9** Проблемы критика попадают в ответ клиенту в поле `problems` и не меняют
  `state`, `turn` и `log`.

**Инварианты.**

- Критик не вызывает модель и не тратит токены.
- Критик не правит состояние и не отменяет ход.
- Критик не зависит от порядка вызова: результат определяется только входами.
- Список проблем не дублирует одну и ту же формулировку дважды (по одному правилу — одна строка).

**Что НЕ входит.** Модель-критик, сверка сущностей и цифр с прозой, повторная генерация
по провалу, оценка литературного качества, автоматическое исправление прозы.
Повтор хода после провала в PRG отсутствует: если он нужен, он добавляется отдельным блоком
и отдельными критериями.

## Блок 11. Ход целиком (оркестрация)

**Статус в PRG:** реализовано; порядок и отсутствие ретрая зафиксированы ниже как контракт.

**Цель.** Один вызов движка превращает ввод игрока в применённые изменения, запись лога,
снимок и отчёт о стоимости.

**Входы.** Сессия, ввод игрока, необязательный колбэк стрима.

**Выходы.** `TurnStats`; после серверной части — снимок, файл кампании, ответ клиенту.

**Поведение.**

- Контекст собирается до изменения состояния; в блоке состояния стоит номер прошлого хода.
- Ведущий вызывается один раз: стрим — только если ожидается чистая проза (state-агент
  включён) и у модели есть стрим; иначе цельный вызов.
- `state.turn` увеличивается на 1 до применения дельты.
- Дельта применяется, если она есть; пустая дельта не вызывает ошибок.
- Критик получает состояние после применения дельты.
- В лог добавляются две записи с одним номером хода: ввод и проза.
- Стоимость: `fresh = max(tokensIn − cached, 0)`;
  `cost = fresh·priceIn + cached·priceCached + tokensOut·priceOut` (цены за 1M токенов).
- Расход прибавляется к счётчикам сессии и к расходу агента `gm`.
- В серверной части: state-агент и суммаризатор выполняются параллельно; падение любого
  не отменяет ход; снимок пишется после их применения; файл перезаписывается.
- Если ввод игрока содержит «обещаю/клянусь/дам слово», а state-агент не вернул обещание,
  обещание добавляется принудительно.

**Критерии приёмки.**

- **C11.1** На первом ходе блок состояния в запросе содержит «ход 0», а возвращённый
  `stats.turn` равен 1 (контекст собран до инкремента).
- **C11.2** После хода `log` содержит две последние записи с одинаковым `turn`: `player`
  с введённым текстом и `gm` с прозой.
- **C11.3** Если критик вернул проблемы, ход не отменяется: `turn` увеличен на 1, в логе
  две записи, `problems` непуст.
- **C11.4** При `tokensIn = 1000`, `cached = 400`, `tokensOut = 100` и ценах
  `input = 0.0444`, `cachedInput = 0.0014`, `output = 0.1333` за 1M стоимость равна
  `(600·0.0444 + 400·0.0014 + 100·0.1333) / 1e6` с точностью 1e-12.
- **C11.5** После серверного хода `usage.gm.calls` увеличивается ровно на 1.
- **C11.6** При включённом state-агенте ведущий вызывается без `response_format`,
  а изменения применяет state-агент; при выключенном — ровно один вызов ведущего
  со `response_format` и применением его дельты.
- **C11.7** Ввод «обещаю вернуться к закату» при state-агенте, не вернувшем обещание,
  добавляет его в `state.promises`.
- **C11.8** Состояние в снимке хода содержит изменения, применённые state-агентом
  (например, добавленный агентом предмет присутствует в `snapshot.state.items`).
- **C11.9** Если state-агент бросает исключение, ход возвращает 200, изменения ведущего
  сохранены, `summary` соответствует результату суммаризатора (или прежнему значению,
  если и он упал), в лог сервера записана ошибка.
- **C11.10** Если суммаризатор бросает исключение, ответ хода 200, `summary` прежний,
  снимок и файл записаны.
- **C11.11** Ход без ввода отклоняется на входе (400) и не увеличивает `turn`.

**Инварианты.**

- Один ввод — один ход; номер хода монотонно растёт на 1.
- Ход не отменяется из-за провала критика, state-агента или суммаризатора.
- Любой успешный ход оставляет снимок и запись на диске.
- Провал ведущего не оставляет изменений состояния и не пишет снимок.
- Стоимость считается по фактически отправленному контексту и ответу.

**Что НЕ входит.** Повтор генерации по провалу критика, блокировка параллельных ходов
(в PRG отсутствует; см. блок 13), таймаут вызова ведущего, отмена хода игроком.

## Блок 12. Операции над кампанией

**Статус в PRG:** реализовано; удаление и откаты покрыты не всеми тестами.

**Цель.** Создать кампанию, продолжить, откатить ход, переиграть с другим вводом,
переключить ветку, закрыть задачу, выбросить предмет.

**Входы.** HTTP-запросы с id кампании, номером хода, текстом или именем сущности.

**Выходы.** Обновлённое состояние и/или проза; изменённый файл кампании.

**Поведение.**

- Создание: id из запроса или `camp-<timestamp>`; существующий id — 409; в файл пишутся
  тексты, состояние, копия агентов, `initial`, пустые снимки.
- Чтение: состояние, история (лог), конспект (закрытый и текущий), сводка снимков
  `{turn, input, variants}`.
- Перегенерация хода N: откат к снимку N−1, повтор прежнего ввода, прежний ответ становится
  вариантом 1 нового снимка.
- Правка реплики хода N: то же, но с новым вводом.
- Вариант: index 0 — текущий (без изменений), index ≥ 1 — обмен местами с сохранённым
  вариантом; состояние берётся из варианта.
- Выброс предмета: удаление из `items`, запись в архив с причиной «может всплыть позже».
- Закрытие задачи: `done` — архив «выполнено»; иначе `failed` — архив «брошено»,
  крючок «Брошено: …» и дебафф «Репутация под вопросом».
- Удаление кампании: файл удалён, сессия забыта.

**Критерии приёмки.**

- **C12.1** `POST /api/campaigns {id:'новая-игра'}` возвращает 200 с `id`, `state` (`turn = 0`),
  пустой `history`, `totals`, `meta`; файл создан.
- **C12.2** Повторный `POST /api/campaigns` с тем же id возвращает 409 с текстом
  «кампания с таким именем уже есть».
- **C12.3** `DELETE /api/campaign/<id>` возвращает `{ok:true}`; файл отсутствует;
  последующий `GET` даёт 404 «кампания не найдена».
- **C12.4** `GET /api/campaign/<id>` содержит `state`, `history` (равен `state.log`),
  `conspect`, `conspectRecent`, `turns` (`[{turn, input, variants}]`), `map`, `worldMap`,
  `model`, `summary`, `totals`.
- **C12.5** После `regenerate` хода 2 контекст собран из состояния после снимка хода 1
  (в блоке состояния «ход 1»), ввод хода 2 повторён, в снимке хода 2 `variants` ≥ 1,
  а прежняя проза хода 2 доступна как вариант 1.
- **C12.6** После `edit` хода 2 с текстом «новый ввод» запись `player` хода 2 содержит
  «новый ввод», а прежний ответ сохранён вариантом.
- **C12.7** `variant` с `index = 1` меняет `state` и прозу на сохранённые; `index = 0`
  возвращает 200 и не меняет состояние.
- **C12.8** `regenerate` без снимка хода N даёт 404 «нет снимка этого хода»;
  при наличии снимка N, но отсутствии N−1 — 400 «нет снимка предыдущего хода».
- **C12.9** `drop` существующего предмета удаляет его из `items` и добавляет в `archive`
  запись с `kind = 'item'`; `drop` отсутствующего даёт 404 «такого предмета нет».
- **C12.10** `quest` с `action = 'done'` ставит статус `done` и архив «выполнено»;
  с `action = 'abandon'` — статус `failed`, архив «брошено», крючок «Брошено: …»,
  дебафф «Репутация под вопросом».
- **C12.11** Ход с пустым `input` даёт 400 «пустой ход»; 1201 символ — 400 «ход слишком
  длинный»; 1200 символов принимается.

**Инварианты.**

- Любая операция, меняющая кампанию, оставляет файл в согласованном состоянии
  (состояние и снимки соответствуют друг другу).
- После отката лог не содержит записей с номером хода больше целевого.
- Вариант — это честная ветка: переключение меняет состояние, а не только текст.
- Удаление кампании необратимо и не оставляет файла.

**Что НЕ входит.** Удаление произвольного хода из середины, слияние веток, экспорт кампании
в текст, переименование кампании, копирование кампании, восстановление удалённой кампании.

## Блок 13. HTTP API, ошибки, устойчивость

**Статус в PRG:** реализовано; блокировка сессии и таймауты отсутствуют (помечено «сверх PRG»).

**Цель.** Один локальный HTTP-сервер: статика и API, единый формат ошибки, предсказуемое
поведение при сбоях.

**Входы.** HTTP-запросы.

**Выходы.** JSON или SSE; файлы статики и изображений.

**Поведение.**

- Сервер слушает `127.0.0.1`, порт из переменной окружения (по умолчанию 7801).
- Все ошибки — JSON `{error: "<текст>"}`, `Content-Type: application/json; charset=utf-8`,
  `Cache-Control: no-store`.
- Неизвестный путь `/api/*` — 404 «нет такого метода».
- Без ключа провайдера операции, требующие модель, возвращают 500
  «нет OPENROUTER_API_KEY в .env»; чтение списка кампаний и статика работают.
- Статика отдаётся только из каталога `src/web`; выход за его пределы запрещён.
- Стрим: `text/event-stream`, события `delta` (кусок текста), `done` (полный результат),
  `error` (сообщение); поток всегда завершается.
- Изображения отдаются по `/api/images/<file>` с `Cache-Control: public, max-age=86400`.
- Ошибка state-агента или суммаризатора не меняет код ответа хода.
- **(сверх PRG)** Параллельные ходы одной кампании сериализуются: второй запрос ждёт
  завершения первого либо получает 409; потерянных снимков нет.
- **(сверх PRG)** Вызов ведущего ограничен таймаутом 60 с; по истечении — 504 с ошибкой
  «модель не ответила за 60 с», состояние не меняется.

**Критерии приёмки.**

- **C13.1** Любой ответ с ошибкой имеет `Content-Type` с `application/json`, тело —
  объект с единственным обязательным полем `error` строкового типа.
- **C13.2** `GET /api/неизвестно` возвращает 404 и тело `{error:'нет такого метода'}`.
- **C13.3** Без `OPENROUTER_API_KEY`: `POST /api/campaign/<id>/turn` возвращает 500
  с текстом «нет OPENROUTER_API_KEY в .env»; `GET /api/campaigns` возвращает 200.
- **C13.4** Запрос `/%2e%2e/src/core/state.ts` не отдаёт файл: ответ 403 или 404.
- **C13.5** Стрим-ответ имеет `Content-Type: text/event-stream`; кадры разделены пустой
  строкой, содержат `event:` и `data:`; при ошибке модели приходит событие `error`
  и соединение закрывается.
- **C13.6** `GET /api/images/нет-такого.png` возвращает 404 `{error:'картинка не найдена'}`.
- **C13.7** `GET /api/images/<существующий>.png` возвращает 200, `Content-Type: image/png`,
  `Cache-Control: public, max-age=86400`.
- **C13.8** (сверх PRG) Два одновременных `POST .../turn` на одну кампанию не теряют ход:
  после завершения обоих в снимках присутствуют оба номера, `state.turn` равен 2,
  либо второй запрос получил 409 и снимков ровно один.
- **C13.9** (сверх PRG) При задержке провайдера больше 60 с запрос завершается 504,
  `turn` не увеличивается, снимок не создаётся.
- **C13.10** Ошибка в необязательном агенте (state, summarizer) не меняет HTTP-код,
  не откатывает уже увеличенный `state.turn` и не отменяет снимок хода.

**Инварианты.**

- Ошибка любого слоя не оставляет кампанию в состоянии, которое нельзя прочитать.
- API не возвращает ключ провайдера и внутренние пути файловой системы.
- Ответы, меняющие состояние, идемпотентны только там, где это заявлено (GET, variant index 0).
- SSE-поток не оставляет открытого соединения после `done` или `error`.

**Что НЕ входит.** Аутентификация, авторизация, CORS, rate limit, HTTPS, горизонтальное
масштабирование, WebSocket, gzip, кэширование API.

## Блок 14. Интерфейс игрока

**Статус в PRG:** реализовано; часть элементов не покрыта тестами (панель, мобильный вид).

**Цель.** Дать игроку шесть экранов и полный набор действий над кампанией без ручного
редактирования файлов.

**Входы.** Действия игрока: маршрут, ввод, кнопки.

**Выходы.** Отрисованные экраны; HTTP-вызовы; обновлённая лента и панель.

**Поведение.** Экраны и элементы перечислены в `03-ui-and-api.md`, раздел «Экраны».
Обязательны: хеш-роутер, лента повествования, поле ввода с Enter/Shift+Enter, индикатор

сцены, карта помещения в боковом меню, обработка ошибок через всплывающее сообщение.

**Критерии приёмки.**

- **C14.1** Маршруты `#/profile`, `#/stories`, `#/new`, `#/agents`, `#/stats`,
  `#/play/<id>` открывают соответствующий экран; неизвестный маршрут открывает профиль.
- **C14.2** В игре заголовок содержит «ход N · <место>» и обновляется после хода.
- **C14.3** Enter отправляет ход, Shift+Enter добавляет перевод строки; ввод из одних
  пробелов не отправляет запрос.
- **C14.4** Пока ход выполняется, кнопка отправки недоступна; повторная отправка
  того же ввода не создаёт второй ход.
- **C14.5** При стриме текст ответа появляется порциями до завершения хода, индикатор набора
  скрывается при первом куске.
- **C14.6** При обрыве стрима клиент повторяет ход через `/turn` и показывает ответ;
  если и второй вызов неуспешен, показывается сообщение с текстом ошибки.
- **C14.7** Под ответом ведущего есть кнопки «⟳», «✎», «🖼»; блок «‹ n/m ›» показывается
  только при `variants > 1` и переключает вариант.
- **C14.8** Панель состояния содержит секции «Место и время», «Тело», «Деньги», «Снаряжение»,
  а также «Пати», «Знакомые», «Задачи», «Долги и крючки», «Фракции», «Мир», «Места»,
  «Бестиарий», «Кадры», «Закрытое» — последние десять при непустых данных.
- **C14.9** Кнопка «✕» у предмета вызывает `/drop`, и предмет исчезает из панели;
  кнопки «✓»/«↷» у задачи меняют её статус в панели.
- **C14.10** Полоса карточек сцены показывает только персонажей с `present === true`
  и `status === 'alive'`; клик открывает панель и раскрывает карточку этого персонажа.
- **C14.11** Врезка «новая карточка» появляется в ленте один раз на персонажа за кампанию:
  повторный ход с тем же персонажем не добавляет вторую врезку.
- **C14.12** При ширине окна ≤ 900 px панель скрыта, кнопка «состояние» её открывает
  и закрывает.
- **C14.13** На экране «Агенты» переключатель «Чьи настройки правим» меняет область правки;
  при выбранной игре «Сохранить» отправляет `campaign` в теле запроса.
- **C14.14** Мастер новой игры: 4 шага; клик по тегу циклично меняет состояние
  «□ → ✓ → ✕ → □»; кнопка «Собрать историю» последовательно вызывает генерацию тона,
  генерацию мира и создание кампании, затем открывает игру.
- **C14.15** Экран «Истории» показывает список кампаний с кнопками «Продолжить» и «Удалить»;
  удаление требует подтверждения, после успеха строка исчезает.
- **C14.16** Экран «Статистика» показывает плитки «Всего», «Ходов», «Средний ход», «Кэш»,
  «Кадров» и таблицу агентов с колонками «Вызовов», «Вход», «Выход», «Стоимость».

**Инварианты.**

- Клиент не содержит правил применения изменений и не вычисляет состояние сам.
- Любое действие, меняющее кампанию, подтверждается ответом сервера до обновления панели.
- Ошибка сервера видна игроку текстом, а не молчанием интерфейса.
- Ввод игрока не отправляется дважды: повторная отправка возможна только после завершения
  предыдущего запроса.

**Что НЕ входит.** Аутентификация, настройки темы, локализация, клавиатурная навигация
по панели, голосовой ввод, мобильное приложение, офлайн-режим.

## Блок 15. Иллюстрации, карты и статистика

**Статус в PRG:** реализовано; картинки и карты не влияют на ход.

**Цель.** Дополнительный контур: детерминированные карты без модели, иллюстрации по
состоянию, отчёт о расходе.

**Входы.** Название места; название мира и список локаций; запрос на изображение; файлы кампаний.

**Выходы.** ASCII-строки карт; PNG-файл и URL; агрегированная статистика.

**Поведение.**

- Карта помещения: 31×12, рамка из `#`, `@` в центре, `=` в одной из стен, декор `~ , ^ *`,
  PRNG с сидом от названия места; одна и та же строка для одного места.
- Карта мира: заголовок «Карта мира · <название>», сетка 41×17 по умолчанию (сервер просит
  высоту 15), пины локаций, легенда.
- Изображения: режимы `scene`, `portrait`, `card`, `item`, `hero`; промт собирается
  из состояния, а не из прозы; референсы — мастер-лист героя и до трёх референсов пати.
- При ошибке основной модели изображения выполняется откат на резервную; ответ содержит
  `fallback: true` и фактическую модель.
- Результат сохраняется файлом и записывается в состояние: `illustrations[]`, `hero.card`,
  `actor.card`/`actor.portrait`, `item.card`.
- Статистика: сумма по кампаниям, расход по агентам, число кадров, средняя стоимость хода,
  доля кэша, средние токены на ход.

**Критерии приёмки.**

- **C15.1** `renderMap('Площадь')` детерминирован: два вызова дают равные строки; первые
  12 строк имеют длину 31 символ; в строке 0 и строке 11 все символы `#`; символ `@`
  стоит в позиции (6, 15); символ `=` присутствует ровно один.
- **C15.2** Для 10 разных названий мест минимум 9 дают разные схемы (сравнение по первым
  12 строкам).
- **C15.3** `renderWorldMap('Пепел', [{name:'Таверна'}], {height: 15})` начинается строкой
  «Карта мира · Пепел», строки со 2-й по 16-ю имеют одинаковую длину (15 строк сетки)
  и результат детерминирован при повторном вызове.
- **C15.4** `POST /image {mode:'scene'}` возвращает `url`, файл существует в `data/images`,
  `GET` по этому url даёт 200 и `image/png`, в состоянии появилась запись
  `illustrations` с текущим ходом.
- **C15.5** `mode='card'` записывает `actor.card`, `mode='portrait'` — `actor.portrait`,
  `mode='hero'` — `hero.card`, `mode='item'` — `item.card`; у каждого режима свой промт.
- **C15.6** Если основная модель изображения отвечает ошибкой, а резервная успешно,
  ответ содержит `requestedModel` = основная, `model` = резервная, `fallback: true`;
  если обе модели падают — 500 с текстом ошибки.
- **C15.7** `mode='portrait'` с несуществующим именем даёт 404 «персонаж не найден»;
  `mode='item'` с несуществующим предметом — 404 «предмет не найден».
- **C15.8** `GET /api/stats` содержит `totals.campaigns`, `totals.turns`, `totals.cost`,
  `totals.tokensIn`, `totals.tokensOut`, `totals.cached`, `totals.avgCostPerTurn`,
  `totals.cacheHitRate`, `totals.avgTokensPerTurn`, `agents`, `images`.
- **C15.9** `PUT /api/art-tags` обрезает пробелы, удаляет дубликаты и ограничивает каждый
  список 40 элементами; `GET /api/art-tags` возвращает сохранённый выбор; выбранные теги
  попадают в промт как «Дополнительно: …», исключённые — как «Не изображать: …».

**Инварианты.**

- Карты не обращаются к модели и не стоят денег.
- Картинка не меняет прозу, состояние хода и конспект; она добавляет только URL и запись
  о кадре.
- Ошибка иллюстратора не влияет на игру.
- Статистика считается только по сохранённым файлам и не требует живых сессий.

**Что НЕ входит.** Асинхронная очередь изображений, локальные модели рисования,
редактирование изображений, карта с координатами игрока в состоянии, экспорт статистики.
